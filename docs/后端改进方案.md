# MallMate 后端改进方案

更新日期：2026-10-12

本文记录当前后端的能力边界、适合本项目的目标方案和实施优先级。首期目标是完成一个清晰、可追踪的单 Agent 售后系统，不追求一次覆盖大型电商的全部模型。

## 1. 配置管理

### 已完成

- 增加 `development`、`test`、`production` 环境字段。
- `.env` 固定从 `backend/.env` 读取，不再依赖命令运行目录。
- 生产环境若开启演示身份或自动种子数据，应用拒绝启动。
- 预留 Redis、MinIO、大模型提供方、模型名和密钥配置入口。

### 后续补充

- 为测试环境提供独立 `.env.test` 或由测试夹具注入配置。
- 启动时校验 PostgreSQL、Redis、MinIO 和模型所需配置是否齐全。
- 密钥只通过环境变量或密钥服务提供，日志中显示掩码。
- 为模型请求补充超时、最大重试次数和 Token 上限配置。

目标配置至少覆盖：运行环境、数据库、Redis、MinIO、LLM、Embedding、Rerank、CORS、日志等级和文件限制。

## 2. 数据库和事务

### 当前边界

- 使用同步 SQLAlchemy，适合当前同步路由和项目规模。
- 本机默认 SQLite；PostgreSQL 配置已存在，但业务代码还没有使用 pgvector。
- 应用启动仍使用 `create_all`，没有迁移版本。
- 写操作的提交目前由对应业务服务负责，还没有通用 Unit of Work。
- 没有测试数据库隔离、慢查询记录和查询超时策略。

### 落地方案

1. 引入 Alembic，把当前表结构生成首个迁移版本。
2. 应用启动只检查版本，不在生产环境调用 `create_all`。
3. PostgreSQL 配置连接池大小、溢出连接数和等待超时；本轮配置入口已经建立。
4. 订单归属、幂等键、会话归属和知识状态字段建立必要索引。
5. 每个写业务明确一个事务边界；跨多个仓储的写操作由 Unit of Work 统一提交或回滚。
6. 测试使用独立数据库或事务回滚夹具，不能复用开发数据库。
7. 增加数据库就绪检查和慢查询日志。

继续使用同步 SQLAlchemy即可满足首期目标；只有在明确出现大量并发等待且上下游均支持异步时，再整体评估异步 SQLAlchemy，避免同步和异步 Session 混用。

## 3. 数据模型

### 当前边界

- 当前模型覆盖用户、商品、订单、单条物流状态、知识文档、售后单和会话消息。
- 售后单缺少规则版本、附件、审核结果和状态历史。
- 知识库缺少文档切片、有效期和向量。
- 缺少人工工单、Agent 运行轨迹、工具调用和审计记录。
- 状态字段仍以字符串存储，数据库层不能完全阻止非法值。
- 外键删除策略尚未明确。

### 适合首期的扩充

保持数据模型精简，只补充能覆盖主要演示场景的表：

```text
knowledge_chunks        知识片段、来源、版本、有效期和向量
evidence_files          图片附件、归属、对象键和视觉摘要
tickets                 人工工单、队列、摘要和状态
agent_runs              一次 Agent 运行的意图、状态和 trace_id
tool_calls              工具名称、结果摘要、耗时和幂等键
audit_events            关键读取、写入、拒绝和转人工记录
after_sales_events      售后状态变化和审核摘要
```

订单金额、地址等字段按演示需要补充；多包裹和完整物流轨迹暂不纳入本轮。状态在 Python 层使用枚举，并在迁移中增加数据库 CHECK 约束。

## 4. API 数据契约

### 本轮已经改进

- 聊天、订单、物流、售后预览和售后确认都有明确响应模型。
- `intent`、售后类型、订单状态、物流状态和售后状态使用共享枚举。
- 订单号要求为正整数。
- API 字符串自动去除首尾空白，拒绝未声明的额外字段。
- 列表字段使用 `default_factory`，避免共享可变默认值。
- Agent 和 API 共用 `Intent` 枚举，减少两套字符串定义。

### 完整目标方案

- 所有 API 返回明确的 Pydantic 响应模型，不返回 ORM 对象。
- 错误统一为 `code`、`detail`，后续增加 `request_id` 和可选字段错误列表。
- 订单、物流、知识来源、售后申请、工单和附件分别有版本稳定的数据契约。
- 写操作统一要求认证用户、确认凭据和幂等键。
- 分页接口统一使用 `items`、`next_cursor`；时间统一返回带时区的 ISO 8601。
- 对外状态与数据库内部状态通过服务层映射，避免数据库字段变化直接破坏前端。
- OpenAPI 中为字段添加描述和主要错误响应示例。

## 5. 演示数据初始化

### 本轮已经改进

- 种子数据移到 `bootstrap/seed.py`。
- 用户、商品、订单、订单项、物流和知识文档分别检查，可补齐部分缺失数据。
- `seed_demo_data` 提供明确开关，生产环境禁止启用。

### 后续补充

- 建表交给 Alembic，种子数据改为独立命令 `python -m app.bootstrap.seed_cli`。
- 为演示数据增加版本号和更新策略；内容变化时执行受控 upsert。
- 使用数据工厂生成已签收、未发货、越权、重复申请和政策过期等场景。
- 正式环境的数据导入与演示种子完全分离。

## 6. 知识检索与 RAG

### 当前边界

- 使用双字交集进行简单相似度排序。
- 不理解同义词和上下文。
- 没有全文索引、向量检索、文档切片和重排。
- 每次读取所有有效文档，数据量增大后性能较差。
- 没有政策有效期、地区和商品范围过滤。
- 直接返回整篇文档，尚未使用模型依据证据生成答案。

### 改进流程

```text
文档校验和解析
→ 按章节和语义切片
→ 保存版本、有效期、商品和地区元数据
→ 生成 Embedding 写入 pgvector
→ PostgreSQL 关键词召回 + 向量召回
→ RRF 合并和元数据过滤
→ Rerank
→ 证据充分性判断
→ 模型只依据证据生成答案
→ 校验引用 ID 后返回
```

首期先支持 Markdown 政策和商品说明，再增加 PDF/HTML。过期、草稿和不适用商品的片段必须在召回阶段过滤。

## 7. LangGraph Agent

### 本轮已经改进

- `state.py`、`nodes.py`、`graph.py` 分离。
- 图在进程加载时编译一次，不再每个请求重新构建。
- 数据库服务通过 `AgentContext` 注入，不进入可持久状态。
- Agent 不再捕获 FastAPI `HTTPException`，改用领域异常。

### 当前边界

- 意图识别仍是关键词规则，没有大模型结构化输出。
- 没有槽位、历史消息、checkpointer、暂停和恢复。
- 用户确认和售后创建仍在独立 API 中，没有进入图。
- 没有正式工具注册、超时、有限重试和错误节点。
- 人工分支只返回提示，没有创建工单。

### 目标状态

Agent 状态大致扩充为：

```text
conversation_id
authenticated_user_id
messages
intent
slots
order_context
retrieved_evidence
tool_results
risk_level
approval_status
final_response
trace_id
```

目标流程是：加载上下文 → 结构化理解 → 条件路由 → 检索/业务工具 → 结果核验 → 缺字段追问或用户确认 → 写操作 → 状态回查 → 答复/转人工。订单事实、资格和授权始终由业务服务决定。

## 8. 实施优先级

1. 当前工程分层和 API 契约保持稳定。
2. 引入 Alembic，切换并验证 PostgreSQL。
3. 接入正式演示登录和资源授权。
4. 建立知识切片、混合检索和引用。
5. 接入 LLM 结构化输出，升级 LangGraph 多轮状态。
6. 把售后确认、写入和人工工单纳入图。
7. 加入图片证据、运行轨迹、审计和离线评测。
