# MallMate：30 天工程开发与学习计划

> 更新日期：2026-10-12。起点是已经完成分层整理的 FastAPI + LangGraph 工程骨架。计划按个人每天 4～6 小时设计；每一天都包含开发内容、可见产出和必须理解的知识点。

## 目标与使用方法

- **投入假设：** 个人开发，每天约 4～6 小时；建议用 1～1.5 小时学习，2.5～3.5 小时开发，最后 0.5～1 小时验证与记录。天数从实际开始执行的日期计算。
- **第 30 天的“完整”范围：** 一个可演示的单 Agent，覆盖政策/商品问答、本人订单与物流查询、退换货申请、图片证据、投诉建单与人工转接；模型负责理解与表达，业务服务负责事实、资格与写入。退款仅用模拟或人工审核，不接真实支付。
- **每天结束：** 将实际完成项、遇到的问题、运行命令和截图/日志写入 `docs/开发记录.md`；代码和样例提交到 Git。未完成的任务先处理依赖，再顺延后续任务。
- **数据边界：** 政策和售后规则明确标注“演示用”；公开数据只作为结构化数据或问法参考，不冒充真实客服处理记录。
- **磁盘约束：** 项目、虚拟环境、缓存和项目数据继续放在 F 盘；当前 Docker Desktop WSL 数据位于 E 盘。第 5 天须把 PostgreSQL 真正启动，若 Docker 服务仍不可用，就在非 C 盘准备可访问的 PostgreSQL 实例。

## 当前基线与最终验收

当前基线已增加 10 类意图规则、15 篇 Markdown 知识、版本化模拟交易数据、BM25 检索和可执行的离线评估入口。`X-Demo-User` 仍是演示认证；通义千问、ChromaDB 向量检索、Redis 记忆、MinIO 附件与完整多轮 Agent 尚未接入业务流程。目标运行数据库已经确定为 PostgreSQL，SQLite 只保留为轻量本地备用路径。

### 每天的固定执行顺序

1. 从 `docs/开发记录.md` 读取前一天遗留问题，明确当天只改动哪条流程。
2. 用 1 个最小例子理解当天组件，再修改本仓库代码；计划中写出的新路径均表示**待创建文件**。
3. 先检查单个服务/工具的输入输出，再用浏览器或 API 跑通当天场景；记录请求、实际响应和数据库变化。
4. 将新出现的正常、异常和越权场景追加到 `evals/drafts/`，当天结束再写开发记录。

当前后端已完成第一轮分层，现有 `/api/v1/...` 接口保持兼容。后续在下面的结构上增加认证、RAG、工具和检查点：

```text
backend/app/
  api/routes/       # 已有 chat、orders、after_sales、health；后续加 tickets、files
  agent/            # 已有 state、nodes、graph；后续加模型适配和检查点
  core/             # 已有配置、枚举、领域异常；后续加认证和请求 ID
  db/               # Engine、Session 和 Base
  repositories/     # 数据库访问
  services/         # 业务规则、事务和幂等
  schemas/          # API 数据契约
  bootstrap/        # 演示数据准备
  tools/            # 待增加：Agent 可用的受控工具
  rag/              # 待增加：导入、Embedding、检索、重排
  storage/          # 待增加：MinIO 附件访问
  models.py         # 当前规模下集中维护 ORM 模型
backend/alembic/   # 数据库迁移
evals/             # 样例、评测脚本、指标和报告
```

**接口约定：** `GET /health` 保留；现有聊天、订单、物流、售后预览与确认接口路径保持不变。后续新增 `POST /api/v1/auth/login`、`GET /api/v1/auth/me`、`POST /api/v1/files`、`POST /api/v1/tickets` 等接口。写接口由后端校验登录用户、确认凭据、幂等键和业务状态；模型输出只作为待核验的候选参数。

第 30 天按以下清单验收：

1. 四条主流程均可通过网页演示：有来源的 FAQ、授权订单/物流查询、确认后售后申请并回查、图片证据关联与人工转接。
2. 过期/不适用政策不能用于作答；订单事实来自业务库；越权读取和未确认写入均被服务端拒绝。
3. 同一幂等键重复提交只产生一条售后申请；工具失败时给出可理解的结果并记录轨迹。
4. 版本化评测集、自动评测脚本、指标报告和至少 10 个失败案例分析齐备。
5. Docker Compose 或等效的非 C 盘部署路径可复现启动；README 写明数据来源、配置、运行命令和能力边界。

## 第 1 阶段：理解骨架与基础组件（第 1～7 天）

### 第 01 天：认识项目与建立基线

- **学习：** 阅读项目选题、`README.md`、`docs/后端工程架构.md`、`backend/app/main.py`、`api/routes/chat.py` 和 `agent/graph.py`，画出用户请求从页面到数据库的路径；理解 API、仓储、服务、Agent 各自负责什么。
- **开发：** 启动现有前后端，运行 `backend/scripts/smoke.py`；记录当前功能、缺口和至少 20 条中文用户问法，作为初始开发集。
- **具体产出：** `evals/drafts/baseline.jsonl`、一张“前端 → API → Agent/Service → Repository → 数据库”流程图、开发记录中的基线结果。
- **完成标准：** 能口头解释 FAQ、查单、售后确认三条现有路径，以及为什么 Agent 不直接执行 SQL。

### 第 02 天：Python 类型、配置与 Pydantic

- **学习：** Python 3.11 类型标注、异常、虚拟环境、依赖管理；Pydantic 的请求校验、枚举、字段约束和配置读取。
- **开发：** 复核现有 `schemas/`、`core/config.py` 和 `.env.example`；为主要字段补充 OpenAPI 描述和示例，明确开发、测试、生产环境配置表。
- **具体产出：** `docs/configuration.md`、完善后的 OpenAPI 字段说明、三套环境变量清单。
- **完成标准：** 能解释 Pydantic 校验发生在业务函数之前；无效订单号、空原因和错误申请类型得到明确错误。

### 第 03 天：FastAPI 基础

- **学习：** 路由、依赖注入、中间件、异常处理、OpenAPI、同步与异步接口；理解身份应由服务端依赖注入。
- **开发：** 在现有分层路由上增加请求 ID 中间件、统一校验错误格式和基础结构化日志；保持接口路径不变。
- **具体产出：** `core/request_id.py`、统一错误响应示例、一次请求从进入到返回的日志样例。
- **完成标准：** `/docs` 可按模块找到接口；正常和异常响应都可通过请求 ID 关联日志。

### 第 04 天：SQLAlchemy 与数据库迁移

- **学习：** ORM 关系、事务、唯一约束、索引，以及 Alembic 迁移与 `create_all` 的区别。
- **开发：** 给现有模型建立第一版 Alembic 迁移；补全订单、售后、知识文档、工单和审计所需的关键字段，画初版 ER 图。
- **实施细节：** 在 `backend/pyproject.toml` 加入 Alembic，建立 `backend/alembic/`；迁移包含现有表及 `tickets`、`audit_events`、`knowledge_chunks`。把种子数据与建表动作分开；新建空库执行 `upgrade head`、导入种子数据，再查表数和主要外键。ER 图放入 `docs/er.md`。
- **完成标准：** 空库执行迁移后可导入演示数据；数据库结构变更不再依赖应用启动时自动建表。

### 第 05 天：PostgreSQL、pgvector 与 Docker

- **学习：** PostgreSQL 基本查询、索引、事务、角色权限；理解 pgvector 存储向量的作用和 Compose 的服务/数据卷。
- **开发：** 解决 Docker Desktop 服务启动问题并运行 `compose.yaml`，或者准备非 C 盘的 PostgreSQL；执行迁移和演示数据导入，确认 `vector` 扩展可用。
- **实施细节：** 优先运行 `docker compose up -d db`；检查 `infrastructure/postgres/init.sql` 的扩展已创建，再把 `backend/.env` 的数据库地址切到 PostgreSQL。执行迁移和种子脚本，调用订单 `1001` 与售后预览接口。如果 Docker 服务仍不能启动，当天改用安装在非 C 盘的 PostgreSQL，不让后续 RAG 被数据库问题阻塞。
- **完成标准：** 后端通过 PostgreSQL 完成订单查询与售后预览；记录数据库连接方式和数据目录。SQLite 保留作快速本地演示。

### 第 06 天：Redis 与 MinIO 基础

- **学习：** Redis 的缓存、TTL、锁和数据丢失边界；MinIO/S3 的桶、对象键、访问权限与短期链接。
- **开发：** 接通 Redis 与 MinIO 的健康检查，创建演示桶；约定会话缓存键、幂等锁键和附件对象键的命名及过期时间。
- **实施细节：** 新建 `backend/app/core/redis_client.py` 与 `storage/object_store.py`；配置 Redis URL、MinIO endpoint/桶名。写一个仅供本地运行的连通性脚本：设置 60 秒 TTL 键后读取，上传小图片后按对象键读取并删除。约定键名如 `mallmate:session:{id}`，但订单和申请状态始终从业务库取。
- **完成标准：** 可写入/读取一个带 TTL 的 Redis 键，可上传/下载一个演示文件；订单事实仍从 PostgreSQL 读取。

### 第 07 天：Next.js 与前后端联调

- **学习：** React 状态与表单、Next.js Client Component、浏览器请求和 CORS；阅读 `frontend/AGENTS.md` 指向的本地 Next.js 文档。
- **开发：** 整理现有页面的 API 调用与加载/错误状态，增加订单和售后结果的清晰展示；检查窄屏显示。
- **实施细节：** 抽出 `frontend/lib/api.ts` 统一 API 地址、请求头和错误解析；把聊天消息、来源引用、售后表单拆成组件。切换账号时清空会话；编辑售后表单时废弃旧预览；同一预览的确认重试复用同一个幂等键。运行 `npm run build` 并在浏览器复查三条基线流程。
- **完成标准：** 网页可完成现有 FAQ、查单、售后预览/确认；第一周里程碑为“PostgreSQL 上的基础客服可运行”。

## 第 2 阶段：业务事实与知识检索（第 8～14 天）

### 第 08 天：登录身份与权限

- **学习：** 登录态、会话或 JWT 的基本机制，服务端授权与资源归属校验。
- **开发：** 用演示账号登录流程替换可随意伪造的 `X-Demo-User`；订单、会话、售后单查询统一从认证依赖取得用户 ID。
- **实施细节：** 新建 `backend/app/core/auth.py` 和 `api/auth.py`，实现演示账号登录、`/api/v1/auth/me`、退出与 HttpOnly 会话 Cookie；会话记录放 Redis 或数据库并设置过期时间。`current_customer` 改为根据会话查用户；前端请求设置 `credentials: "include"`，后端仅允许明确的前端来源并开启凭据传输，写接口核对 Origin/CSRF 凭据。删除账号请求头。用 Alice 的登录态访问 Bob 的订单和会话，均应得到拒绝响应。
- **完成标准：** Alice 无法通过改请求参数读取 Bob 的订单或会话；未登录请求被拒绝。

### 第 09 天：订单、商品和物流工具

- **学习：** 工具接口设计、输入/输出模式、超时与错误码；区分业务事实与模型生成内容。
- **开发：** 将 `search_product`、`get_order`、`get_logistics` 做成独立业务工具，提供可注入的接口和模拟故障方式。
- **实施细节：** 从 `services.py` 拆出订单/商品查询服务，新建 `backend/app/tools/catalog.py`、`orders.py`。每个工具返回结构化结果，例如 `status`、`data`、`error_code`、`updated_at`；工具只接收已认证的用户上下文和业务参数。准备“无订单号”“多个近期订单”“未发货”“跨用户订单”“数据库超时”五组样例。
- **完成标准：** 每个工具可单独调用并有归属校验；无物流、多个订单和工具超时有明确结果。

### 第 10 天：售后资格与写入规则

- **学习：** 确定性规则、事务、幂等键、并发重复提交、写后回查。
- **开发：** 扩展 `check_eligibility` 和 `create_after_sales_case`，加入规则版本、缺失信息、拒绝原因、确认记录和重复请求保护。
- **实施细节：** 在 `backend/app/tools/after_sales.py` 中分开“资格检查”和“创建申请”。预览时生成与用户、订单、类型、原因绑定且短期有效的一次性确认凭据；确认接口先按幂等键查已有结果，已有同参数申请则直接返回；新申请才验证并原子消耗凭据，同时核对订单归属和当前状态，再在事务内写入。写完以申请 ID 回查。对同一幂等键并发提交两次，只允许产生一条记录。
- **完成标准：** 已签收、未签收、缺原因、重复提交各有预期结果；未经确认不产生售后单。

### 第 11 天：知识文档解析与版本

- **学习：** Markdown/PDF/HTML 提取、章节和表格保留、切分策略、文档元数据与有效期。
- **开发：** 编写导入脚本，先导入演示政策和商品说明；每个片段保存来源、章节、商品范围、版本、状态和有效日期。
- **实施细节：** 新建 `backend/app/rag/ingest.py` 和 `backend/scripts/import_knowledge.py`；先支持 `knowledge/policies/*.md`，再加 PDF/HTML 解析器。按标题和段落切分，给文档算校验和，给片段保存 `document_id`、`section`、`source_uri`、`version`、`effective_from/to`。同一来源与版本再次导入时按校验和更新或跳过。
- **完成标准：** 重复导入可更新而不制造重复片段；抽样查看 10 个片段时可定位回原文。

### 第 12 天：Embedding 与向量检索

- **学习：** Embedding、向量维度、相似度、召回率，以及模型更换时重建索引的影响。
- **开发：** 定义可替换的 Embedding 接口，把知识片段写入 pgvector；建立向量检索函数和小型检索样例集。
- **实施细节：** 新建 `backend/app/rag/embedding.py`，定义 `embed_documents(texts)` 与 `embed_query(text)`；按所选模型维度给 `knowledge_chunks` 增加向量列和索引。导入脚本只为新增/变更片段生成向量；查询接口返回前 10 个片段的 ID、分数和版本。先用 10 条同义改写问题核对召回。
- **完成标准：** 给定 10 条改写问题，可返回对应政策或商品片段；记录模型名称、维度和索引版本。

### 第 13 天：全文检索与混合召回

- **学习：** PostgreSQL 全文检索、关键词匹配、RRF 合并；中文分词或字词切分的局限。
- **开发：** 并行执行关键词和向量召回，合并去重；在召回前过滤草稿、过期、地区/商品不适用文档。
- **实施细节：** 为中文片段增加可检索的分词字段及 GIN 索引，查询问题使用相同切词方式；新建 `backend/app/rag/retriever.py`，分别取关键词 Top 20、向量 Top 20，按片段 ID 用 RRF 合并。先在 SQL 条件中过滤文档状态、日期、商品和地区，再打印两路排名与合并排名供人工检查。
- **完成标准：** 同一问题可查看两路候选和最终排序；过期政策无法进入回答证据。

### 第 14 天：重排与证据充分性

- **学习：** Rerank、Top-K、引用粒度、无依据回答；理解 Recall@K、MRR、NDCG 的含义。
- **开发：** 加入重排接口和证据阈值，输出引用元数据；对 20～30 条检索问题做首次人工标注和指标计算。
- **实施细节：** 新建 `backend/app/rag/rerank.py` 与 `evidence.py`；对合并后的前 10 个片段重排，保留前 3～5 个可引用片段。证据对象包含片段 ID、原文、标题、版本和有效期；阈值只用开发集调节。把“退货上门取件要多久”及无依据问题加入 `evals/drafts/retrieval.jsonl`，输出 Recall@5 和引用核对表。
- **完成标准：** FAQ 回答能指向具体片段；证据不足时明确追问或转人工；第二周里程碑为“可评估的混合检索”。

## 第 3 阶段：完整 Agent 工作流（第 15～21 天）

### 第 15 天：大模型接口与结构化输出

- **学习：** Prompt 的角色、结构化输出、工具调用、Token/成本、超时与重试；识别模型不可靠输出。
- **开发：** 封装可配置 LLM 适配层，增加真实模型与本地模拟两种模式；让模型只产出意图、槽位候选和答复草稿。
- **实施细节：** 新建 `backend/app/agent/llm.py` 与 `prompts.py`；用 `IntentResult(intent, slots, confidence, needs_human)` 作为结构化输出模型。模型地址、名称、密钥和超时从环境变量读取，密钥不进 Git；模拟适配器返回固定结果供离线开发。对格式错误输出只重试有限次数，仍失败则转人工/追问。
- **完成标准：** 模型输出须通过 Pydantic 校验；缺失或错误的订单号不会被当作事实写入业务库。

### 第 16 天：LangGraph 状态与路由

- **学习：** State、节点、条件边、检查点、`interrupt`/恢复的用途。
- **开发：** 将现有关键词图升级为结构化状态：会话 ID、用户 ID、意图、槽位、证据、工具结果、风险、确认状态和 trace ID；加入条件路由。
- **实施细节：** 新建 `backend/app/agent/state.py`，把当前 `workflow.py` 的五个字段扩展为完整状态；按 `load_context → parse → route → retrieve/tool → verify → respond` 拆节点。用 `conversation_id` 关联持久化检查点，明确哪些字段可跨轮保存、哪些只在本轮使用；画实际状态图到 `docs/agent-state.md`。
- **完成标准：** 同一个对话在下一轮可恢复槽位；能从轨迹看出每次经过的节点。

### 第 17 天：政策与商品 FAQ 流程

- **学习：** 检索增强生成的提示约束、引用核对和无法回答时的降级方式。
- **开发：** 连接“识别问题 → 检索 → 检查证据 → 生成带引用答复”；支持商品规格与政策 FAQ 两个知识域。
- **实施细节：** 在 Graph 中增加 `retrieve_knowledge`、`check_evidence`、`compose_answer` 节点；把检索片段作为唯一可引用上下文传给模型。生成后核对引用 ID 必须来自本轮检索结果，政策类回答还要核对版本/有效期。证据不够时返回“无法确认”及下一步，而不是补写时效或规则。
- **完成标准：** 5 条有依据问题引用正确片段；5 条无依据/过期政策问题不编造答案。

### 第 18 天：订单与物流流程

- **学习：** 实体抽取、缺槽位追问、多订单消歧，以及工具结果到自然语言的映射。
- **开发：** 连接订单/物流工具；订单号缺失时追问，用户有多个订单时提供选择，返回状态与更新时间。
- **实施细节：** 新增 `collect_order_slot`、`load_owned_orders`、`get_logistics` 节点。若用户只说“我的订单到哪了”，先查本人近期订单并给出最多 3 个可辨认选项；下一轮将用户选择映射到订单 ID，再由工具查归属和物流。回答模板只使用工具返回的状态、商品与更新时间。
- **完成标准：** 用户连续两轮补充订单号后能得到本人订单结果；跨用户订单仍被服务端拒绝。

### 第 19 天：退换货暂停与恢复

- **学习：** 人机确认点、检查点持久化、写操作前置校验、执行后核验。
- **开发：** 实现“收集槽位 → 查订单/政策 → 资格检查 → 预览 → 等待确认 → 创建申请 → 回查”；支持中途退出和恢复。
- **实施细节：** 在 Graph 中增加 `collect_case_slots`、`check_eligibility`、`preview_case`、`await_confirmation`、`create_case`、`verify_case`。缺订单/原因时保存状态并追问；预览时保存规则版本与确认凭据；恢复时重新核对用户、订单状态和凭据。若写工具返回超时，先按幂等键查询既有申请，再决定是否重试。
- **完成标准：** 未确认时数据库无新申请；确认后返回同一个申请编号，重复确认不会重复创建。

### 第 20 天：投诉工单与人工转接

- **学习：** 工单生命周期、风险分级、转人工触发条件和交接摘要。
- **开发：** 增加 `create_ticket`、`handoff_to_human`，保存问题摘要、已核验订单、证据来源、失败原因和会话轨迹。
- **实施细节：** 创建 `tickets` 表与 `backend/app/api/tickets.py`、`tools/tickets.py`；工单记录队列、优先级、状态、会话 ID 和可访问的附件 ID。Graph 的 `handoff` 分支只携带已核验订单、检索来源与失败原因。客服诊断页提供按工单号查看交接摘要，用户端只显示工单号和当前状态。
- **完成标准：** 用户主动要求人工、规则冲突、工具连续失败都能建单；客服端能看见完整交接信息。

### 第 21 天：失败处理与多轮回归

- **学习：** 有限重试、超时预算、幂等恢复、对话状态清理和异常分支设计。
- **开发：** 处理模型格式错误、检索为空、工具超时和用户改口；补齐相关回归样例。
- **实施细节：** 为只读工具设置超时和至多两次重试，写工具仅通过同一幂等键恢复；用户改订单号时清除旧订单和旧确认凭据。把“查单后改问退货”“模型返回非法 JSON”“知识为空”“物流工具超时”加入开发集，运行完整会话而非单轮问答。
- **完成标准：** 四条文字主流程端到端跑通；失败时可追踪、可重试或转人工。第三周里程碑为“完整文字版 Agent”。

## 开发时固定的三个数据契约

这些字段是后续开发的目标结构，当前骨架尚未全部实现。先固定契约，再分别完成接口、工作流和前端，可以减少反复改字段。

### 售后预览与确认（第 10、19 天）

`POST /api/v1/after-sales/preview` 的目标响应示例：

```json
{
  "eligible": true,
  "missing_fields": [],
  "blocking_reasons": [],
  "policy_version": "demo-v2",
  "preview_token": "短期一次性凭据",
  "expires_at": "有效期时间"
}
```

确认时提交相同订单、类型、原因、`preview_token` 和 `confirmed: true`，并在请求头提交 `Idempotency-Key`。服务端核对参数和凭据绑定关系；重复请求先按幂等键返回原申请，新的请求才执行资格检查与写入。

### Agent 状态（第 16 天）

| 状态字段 | 来源 | 使用规则 |
|---|---|---|
| `authenticated_user_id` | 认证中间件 | 只能由服务端写入，不能采纳模型输出 |
| `intent`、`slots` | 模型候选结果 | 经结构校验；缺失订单号时追问 |
| `order_context`、`tool_results` | 业务工具 | 订单、物流和资格的事实来源 |
| `retrieved_evidence` | 检索服务 | 保存片段 ID、来源、版本与有效期 |
| `approval_status` | 服务端确认流程 | 控制写工具是否可进入 |
| `conversation_id`、`trace_id` | API/工作流 | 关联多轮状态、审计与评测轨迹 |

### 评测用例（第 26 天）

`evals/dataset/*.jsonl` 每行一个 JSON 对象。下面是字段示例，ID 应替换为导入知识后的真实片段 ID：

```json
{"case_id":"faq_001","scenario":"policy_faq","input_messages":["退货上门取件要多久？"],"user_id":"alice","attachments":[],"expected_intent":"policy_faq","required_slots":[],"expected_tools":["search_knowledge"],"expected_source_ids":["return_policy_chunk_03"],"expected_business_result":"no_write","should_handoff":false}
```

评测脚本额外记录 `actual_result`、`pass`、`failure_reason`、模型版本、知识版本和规则版本。业务断言读取数据库最终状态；引用正确性核对实际返回的片段 ID。
