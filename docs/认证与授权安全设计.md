# MallMate 认证与授权开发方案

更新日期：2026-10-13

> 实施状态：第一版已经完成。默认本机配置使用正式登录链路；`X-Demo-User` 只保留为显式关闭认证后的开发回退，不参与正常前端请求。

## 1. 开发目标

第一版认证只解决以下问题：

1. 用户可以使用账号和密码登录。
2. 后端可以从访问令牌中取得可信用户身份。
3. 顾客只能访问自己的订单、物流、售后单和会话。
4. 客服、管理员和顾客拥有不同接口权限。
5. Agent 调用工具时沿用后端认证结果，不能根据聊天内容修改身份。
6. 密码、令牌和 API Key 不写入代码、日志或 Git 仓库。

暂不开发第三方登录、多租户、管理员 MFA、复杂权限策略和完整账号找回流程。

## 2. 当前项目基础

当前代码已经具备以下认证和授权基础：

- `Customer` 是订单、售后单和会话的归属主体。
- `UserAccount` 保存登录账号，`Customer.user_account_id` 连接顾客业务资料。
- `get_current_principal` 验证 Bearer JWT 并生成服务端可信身份。
- `get_current_customer` 只从可信身份取得当前顾客，不读取请求体中的顾客 ID。
- 查询订单时同时使用 `order_id` 和 `customer_id`，可以阻止跨顾客读取。
- 创建售后单时，顾客 ID 来自后端依赖，不从请求体读取。
- Agent 通过运行上下文接收 `Principal`，身份不会写入可持久化 State。
- 生产环境配置禁止演示身份、自动种子数据、弱 JWT 密钥和默认基础设施密码。

当前剩余工作主要是登录限流、审计事件、客服工单授权范围和管理员 MFA。

## 3. 第一版认证方案

采用以下组合：

```text
账号密码登录
    ↓
短期访问 JWT（15 分钟）
    ↓
HttpOnly Cookie 保存刷新令牌（7 天）
    ↓
PostgreSQL 保存可撤销的刷新会话
```

选择该方案的原因：

- FastAPI API 可以独立验证访问令牌。
- 访问令牌有效期短，泄露后的影响时间有限。
- 刷新令牌不放入 `localStorage`，减少被前端脚本读取的风险。
- 退出登录、停用账号或修改密码时，可以撤销数据库中的刷新会话。

## 4. 数据模型

### 4.1 登录账号

新增 `UserAccount`：

```text
UserAccount
  id
  username_normalized    唯一登录名
  password_hash          Argon2id 哈希
  role                   customer / support / admin
  status                 active / locked / disabled
  created_at
  updated_at
  password_changed_at
```

第一版每个账号只有一个角色，因此暂时不创建独立的多角色关系表。

### 4.2 顾客关联

在现有 `Customer` 增加：

```text
user_account_id    可空、唯一、外键关联 UserAccount.id
```

顾客账号必须关联 `Customer`。客服和管理员账号可以没有顾客资料。

### 4.3 刷新会话

新增 `AuthSession`：

```text
AuthSession
  id
  user_account_id
  refresh_token_hash     只保存令牌哈希
  created_at
  expires_at
  revoked_at             未撤销时为空
```

刷新令牌使用高熵随机字符串。数据库不保存令牌原文。

## 5. API 设计

新增以下接口：

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/api/v1/auth/login` | 验证账号密码，返回访问令牌并设置刷新 Cookie |
| `POST` | `/api/v1/auth/refresh` | 撤销旧刷新会话，签发新访问令牌和刷新令牌 |
| `POST` | `/api/v1/auth/logout` | 撤销当前刷新会话并清除 Cookie |
| `GET` | `/api/v1/auth/me` | 返回当前账号、角色和顾客信息 |

登录请求示例：

```json
{
  "username": "demo-alice",
  "password": "用户输入的密码"
}
```

登录响应不返回刷新令牌：

```json
{
  "access_token": "短期 JWT",
  "token_type": "bearer",
  "expires_in": 900
}
```

刷新令牌由后端写入 `HttpOnly` Cookie。

## 6. FastAPI 依赖

业务接口现在使用以下依赖：

```text
get_current_user
  验证 JWT 签名、有效期、签发者和受众
  查询账号并检查账号状态

get_current_customer
  调用 get_current_user
  要求账号角色为 customer
  返回账号关联的 Customer

require_role("support", "admin")
  检查当前账号是否具有接口要求的角色
```

建议创建可信身份对象：

```python
@dataclass(frozen=True)
class Principal:
    account_id: int
    role: str
    customer_id: int | None
```

`Principal`只能由认证依赖创建，不能从请求体、URL参数或模型输出创建。

## 7. 资源授权规则

角色权限只能决定“能否进入某类接口”，具体资源仍要在 Service 或 Repository 中检查。

| 资源 | 顾客 | 客服 | 管理员 |
|---|---|---|---|
| 订单和物流 | 只能查询自己的 | 后续按工单范围查询 | 按管理接口查询 |
| 售后申请 | 只能操作自己的 | 后续按工单处理 | 可以管理 |
| 会话和消息 | 只能读取自己的 | 后续按工单查看 | 按审计规则查看 |
| 知识库维护 | 无权限 | 可配置有限权限 | 可以管理 |
| 账号管理 | 无权限 | 无权限 | 可以管理 |

顾客订单查询必须保持当前模式：

```python
select(Order).where(
    Order.id == order_id,
    Order.customer_id == authenticated_customer_id,
)
```

请求体中的 `customer_id` 不代表权限。创建售后单时仍从认证依赖取得顾客 ID。

## 8. Agent 权限边界

Agent 只接收服务端已经验证的身份：

```text
FastAPI 验证 JWT
    ↓
生成 Principal
    ↓
注入 AgentContext
    ↓
Agent 工具调用 Service
    ↓
Service 再次检查资源归属和业务规则
```

必须遵守：

- 用户在对话中说“我是管理员”不会改变权限。
- 模型可以提取订单号，但不能决定订单归属。
- 查询工具默认只读。
- 创建售后单仍要求用户确认、资格检查和幂等键。
- JWT、刷新令牌、密码和数据库 Session 不写入 LangGraph State。
- 工具只把必要的订单和物流信息返回给模型。

## 9. 密码与令牌要求

### 密码

- 使用 `pwdlib[argon2]`生成和验证密码哈希。
- 不保存明文密码，不使用普通 SHA-256 直接保存密码。
- 登录失败统一返回“用户名或密码错误”。
- 账号不存在时也执行一次虚假密码哈希验证，减少响应时间差异。

### JWT

访问令牌只保存必要声明：

```json
{
  "sub": "账号ID",
  "iss": "mallmate-api",
  "aud": "mallmate-web",
  "iat": 1790000000,
  "exp": 1790000900,
  "jti": "随机ID"
}
```

后端必须固定允许的签名算法，并验证 `exp`、`iss` 和 `aud`。JWT中不保存密码、地址、API Key等敏感信息。

### 刷新令牌

- 使用安全随机数生成。
- Cookie设置`HttpOnly`。
- 生产环境设置`Secure`和`SameSite=Lax`或`Strict`。
- 每次刷新都撤销旧会话并创建新会话。
- 退出登录、账号停用和修改密码后撤销该账号的刷新会话。

第一版允许已经签发的访问JWT继续有效到15分钟后过期，不额外维护访问令牌黑名单。

## 10. CORS 与 CSRF

当前项目的前端和后端端口不同。启用刷新Cookie后，FastAPI需要：

```python
allow_origins=["http://localhost:3000"]
allow_credentials=True
```

不能在启用凭据时使用通配来源。前端刷新和退出请求需要：

```typescript
fetch(url, {
  method: "POST",
  credentials: "include"
})
```

`/auth/refresh`和`/auth/logout`依赖Cookie，应校验`Origin`；正式部署时再增加CSRF Token。

## 11. 配置项

在`Settings`和`.env.example`增加：

```env
MALLMATE_AUTH_ENABLED=true
MALLMATE_JWT_SECRET=
MALLMATE_JWT_ALGORITHM=HS256
MALLMATE_JWT_ISSUER=mallmate-api
MALLMATE_JWT_AUDIENCE=mallmate-web
MALLMATE_ACCESS_TOKEN_MINUTES=15
MALLMATE_REFRESH_TOKEN_DAYS=7
MALLMATE_COOKIE_SECURE=false
```

生产环境必须拒绝：

- 缺少JWT签名密钥。
- 使用默认或过短的签名密钥。
- 开启`demo_mode`或自动演示数据。
- 使用默认数据库或MinIO密码。
- CORS仍配置为不受控来源。

## 13. 已完成的开发顺序

### 第一步：数据库

1. 引入Alembic。
2. 创建`UserAccount`、`AuthSession`。
3. 给`Customer`增加`user_account_id`。
4. 创建开发账号并保存Argon2id密码哈希。

### 第二步：登录

1. 实现密码哈希和验证。
2. 实现JWT签发和校验。
3. 实现`login`和`me`接口。
4. 保留开发环境演示身份，生产环境禁止回退。

### 第三步：刷新和退出

1. 创建刷新会话。
2. 设置HttpOnly Cookie。
3. 实现刷新轮换和退出撤销。
4. 修改CORS和前端`credentials`配置。

### 第四步：授权

1. 已替换受保护路由的演示身份依赖。
2. 已检查订单、物流、售后和会话归属。
3. 已增加客服和管理员角色依赖。
4. 已将 `Principal` 注入 Agent 工具上下文。

## 14. 验收标准

- [ ] 修改`X-Demo-User`不能冒充正式用户。
- [ ] 缺少、伪造、过期或错误受众的JWT返回401。
- [ ] 被停用账号不能继续访问受保护接口。
- [ ] 顾客A不能访问顾客B的订单、物流、售后单和会话。
- [ ] 修改请求体中的`customer_id`不能改变资源归属。
- [ ] 顾客不能访问客服或管理员接口。
- [ ] 对话中的伪造身份不能改变Agent工具权限。
- [ ] 售后写入仍要求确认、资格校验和幂等键。
- [ ] 退出登录后刷新令牌失效。
- [ ] 日志和Agent轨迹不包含密码、完整令牌或API Key。
- [ ] 生产环境缺少JWT密钥或开启演示身份时启动失败。

## 15. 当前结论

该方案适合MallMate当前架构，但应分阶段实现。第一版完成账号密码、短期JWT、刷新会话、三种角色和资源归属即可。认证功能完成后，再继续开发登录限流、审计事件、客服工单范围和管理员MFA。
